# T8160 Home Assistant hardware evidence, 2026-09-11

[Story #55](https://github.com/keesmod/eufy-mega-client/issues/55) covers one
T8160 eufyCam, camera firmware 3.4.3.0, behind its actual T8030 HomeBase 3,
firmware 3.8.6.0. This is one exact local-LAN hardware tuple. It does not
establish support for every T8160 firmware or another eufyCam model or owner.

## Software and environment

The tested build is public client 0.10.0, camera bridge and integration
0.7.1 from camera commit `4641da9ea2e02cda2d2165b9526ab8c4d01de051`, Node
24.21.0 and Home Assistant 2026.9.1 on amd64. Client 0.10.0 comes from
`41690f73f1ed4397f378a6eb9ba6612fc41d998a`, with the published package and
consumer lockfile integrity retained.

The camera [release validation](https://github.com/keesmod/ha-eufy-cam/actions/runs/34580518521)
passed, including HA, browser, bridge, HACS, Hassfest, package and dependency
checks. The [client merged-main validation](https://github.com/keesmod/eufy-mega-client/actions/runs/34577148234)
passed. A fresh local build and all 72 bridge tests passed for the exact 0.7.1
source. These software results do not substitute for the device results below.

The normal Mega bridge was the sole device owner. The previous security
websocket app and integration were stopped or disabled. The test VM was stopped.
All fifteen existing HA entity identities and the dashboard and automation files
were preserved. Camera and mower credentials and processes remained separate.

identifiers and event data were not published.

## Temporary observer and recovery

A temporary wrapper on the existing client's returned values established that
the selected camera's actual owner matched T8030 and that its own reported
availability was online. It created no additional client, command or retry.
The wrapper returned the original handles and observed their completion values.

The first temporary candidate failed because copied private files and their
parent were owned by root while the bridge runs as UID 1000. The normal bridge
was restored. The test helper was corrected for file ownership and for
Supervisor removing stopped app containers. Its original lock option was also
incompatible with the host's BusyBox implementation. These were temporary test
helper defects, not changes to the released client or bridge.

The corrected helper passed local fault simulations with an absent original
container and a transient Supervisor start failure. Its actual lock semantics
were checked on the host. A real switch, candidate readiness, explicit recovery
and subsequent HA identity/snapshot readback then passed. Prior code and private
data were backed up. The normal 0.7.1 release and its original data were retained.

Two earlier cancellation attempts used the Supervisor HTTP proxy. Both transfers
completed and therefore failed the in-flight cancellation acceptance criterion.
The installed proxy buffers non-streaming responses before returning them. The
actual HA app test avoided that test-connection limitation and obtained the
matching device cancellation result. No product fix was needed.

This evidence does not close any family or epic. Remaining model tuples,
other owners, camera migration and legacy retirement stay open in their linked
programme stories.
