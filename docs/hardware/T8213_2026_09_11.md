# T8213 Home Assistant hardware evidence, 2026-09-11

[Story #58](https://github.com/keesmod/eufy-mega-client/issues/58) validates one
T8213 battery doorbell, firmware 0.2.1.8, behind its actual T8030 HomeBase 3,
firmware 3.8.6.0, on the existing local LAN-derived Mega profile. This does not
establish support for another model, firmware or owner combination.

## Software and ownership

The tested software is public client 0.10.0, bridge and integration 0.7.1,
Node 24.21.0 and HA 2026.9.1. The camera release commit is
`4641da9ea2e02cda2d2165b9526ab8c4d01de051`. The client package comes from
`41690f73f1ed4397f378a6eb9ba6612fc41d998a`. The exact running camera image was
verified against the retained release image before each temporary switch.

Client #26 and camera #19 were closed at intake. Predecessor #55 and PR #107
were verified accepted, with successful merged-main CI. Their software and
T8160 results do not substitute for the T8213 measurements below.

The production Mega bridge was the sole controller. Its legacy security app was
stopped and legacy integration disabled. Contrary to the earlier handover,
the test VM was running. Current inspection found no camera bridge container and
no listener at the old integration's configured local bridge endpoint. The VM
therefore had no active camera owner and was left unchanged.

Private backups preserve integration files, camera data and configuration.
All fifteen HA entity identities and dashboard and automation hashes were
checked. Camera and mower credentials and processes remained separate.

## Test method and limitations

A temporary wrapper observed returned values and completion handles of the
existing client instance. It created no additional controller, command or retry.
The normal bridge stopped before the same release image ran with that wrapper.
Its private data was copied from a backup, with correct runtime ownership.
A bounded timer could restore the unchanged normal installation.

Two initial UI cancellation attempts completed the device transfer before the
dialog closed. They are excluded from in-flight cancellation acceptance. The
successful test closed immediately after the UI reported preparation, and the
matching original device handle reported positive bytes and confirmed stop.

An initial post-cancel helper required the idle HomeBase connection to remain
connected before issuing a new query. It observed disconnected and stopped.
The original installation was restored successfully. The follow-up test repeated in-flight cancellation and then issued a new HA
recording query without restarting the bridge. The connection changed from
disconnected to connected, all seven recordings returned with complete true,
and no active or quarantined streams remained. The idle connection flag was
therefore not a valid prerequisite for attempting that recovery query.

No production code change or new release was required for the results above.
Final recovery verified the original image, the sole normal camera bridge, no
loaded observer, no active candidate marker or timer, preserved identities and
a newly decoded stored snapshot. HA configuration validation passed.

Only redacted outcomes are published. Tokens, complete device identifiers,
recordings, snapshots and raw events remain private.
